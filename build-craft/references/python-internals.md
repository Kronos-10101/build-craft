# Python Internals — production checklist

How CPython actually runs and how to optimize it: bytecode, the GIL, profiling-first discipline, faster runtimes, native extensions, concurrency models, and micro-optimizations. Complements `references/python.md` (style/tooling). Checked 2026-09-30.

## How Python runs: bytecode & the eval loop

- [ ] You can name the pipeline: source → AST → bytecode (`dis.dis(f)`) → the CPython eval loop (`_PyEval_EvalFrameDefault`) executing one opcode at a time.
- [ ] Know that every Python-level operation (attribute lookup, call, `+`) is interpreter dispatch overhead — the win is doing less Python, not faster Python.
- [ ] `sys.getsizeof` + `dis` used to verify assumptions about object overhead and generated bytecode before "optimizing".
- [ ] Startup cost attributed with `python -X importtime` — heavy imports moved lazy or behind the CLI subcommand that needs them.

## The GIL: what it blocks, and free threading

- [ ] The GIL is a per-process mutex: only one thread executes Python bytecode at a time (releases between bytecodes ~every 5 ms via `sys.setswitchinterval`, and around I/O).
- [ ] CPU-bound pure-Python threads do NOT parallelize on a GIL build — they interleave; `threading` is for I/O concurrency and GIL-releasing native code only.
- [ ] `threading` picked for I/O-bound work (sockets, files — the GIL releases while waiting); `multiprocessing`/`ProcessPoolExecutor` for CPU-bound work; `asyncio` for many concurrent I/O ops in one thread.
- [ ] Free-threaded CPython (PEP 703): experimental `python3.13t`, officially supported from 3.14 — threads truly run in parallel, but code that was "accidentally thread-safe" under the GIL now races; extensions that don't declare `Py_MOD_GIL_NOT_USED` silently re-enable the GIL process-wide.
- [ ] Parallelism advice states its interpreter assumption: "on GIL builds (the default), use multiprocessing for CPU-bound work."

## Profile before optimizing

- [ ] A profile artifact exists before any optimization: no guessing, no "it feels slow".
- [ ] `python -m cProfile -s cumulative` (stdlib, deterministic, exact call counts) used in dev — trust relative rankings, not absolute percentages (instrumentation overhead).
- [ ] `py-spy record -o flame.svg` (sampling, near-zero overhead, attaches to a live PID) used in production — never `cProfile` on a live service; use `--nonblocking` on latency-sensitive ones.
- [ ] `line_profiler` (`kernprof`) used only after the hot *function* is known, to find the hot *line*.
- [ ] Memory growth diagnosed with `tracemalloc` snapshots, not guesses; `@lru_cache` always has a `maxsize` on long-lived processes.

## Algorithmic wins first

- [ ] Big-O reviewed before any micro-optimization: an O(n²)→O(n) fix beats any interpreter trick by orders of magnitude.
- [ ] Hot loops pushed into C: vectorize with NumPy/pandas ops instead of Python `for` loops; `iterrows()` replaced with column ops.
- [ ] Lookup structures correct: `set`/`dict` for membership (O(1)), not list scans; repeated work memoized or precomputed.
- [ ] I/O batched: one bulk query/insert instead of N round trips; the network/DB is usually the bottleneck, not the eval loop.

## Faster runtimes & native extensions

- [ ] **PyPy** evaluated for long-running pure-Python CPU workloads (JIT, often 2–10×) — rejected when C-extension compat (NumPy historically) or warmup time rules it out.
- [ ] **Numba** (`@numba.njit`) picked for numeric hot loops on NumPy arrays — near-C speed, no rewrite; types must be stable or it falls back to object mode.
- [ ] **Cython** picked when you need C-level control, GIL release (`nogil`), or to wrap C libraries; `.pyx` compiled in CI, not committed as generated C.
- [ ] **mypyc** picked to speed up already-type-annotated Python by compiling it — cheapest path when the codebase is fully typed.
- [ ] Rule: profile → algorithmic fix → vectorize → Numba/Cython — never start at Cython.

## Concurrency model choice

- [ ] I/O-bound, thousands of connections → `asyncio` (one thread, no GIL contention, no IPC overhead); blocking calls wrapped with `run_in_executor`.
- [ ] I/O-bound, simple fan-out → `ThreadPoolExecutor`; CPU-bound → `ProcessPoolExecutor` with picklable top-level functions.
- [ ] Shared state between processes via explicit channels (queues/pipes/shared memory), never ad-hoc globals; `multiprocessing` spawn cost budgeted at startup, not per request.
- [ ] On free-threaded builds (3.14t+): `threading` becomes viable for CPU work, but every shared-mutable structure gets real locks — audit before assuming.

## Micro-optimizations (only after profiling)

- [ ] `__slots__` on classes with millions of instances — kills per-instance `__dict__`, big memory win; skipped when dynamic attributes are needed.
- [ ] Zero-copy buffers: `memoryview`/`bytes`/`bytearray` for binary parsing; no `bytes(x)` copies in the hot path.
- [ ] String building: `''.join(chunks)` over `+=` in loops; f-strings over `%`/`.format`; regexes precompiled at module level.
- [ ] Attribute/method lookup hoisted out of loops (`append = lst.append`); module-level constants, not recomputed literals.
- [ ] Import time: `python -X importtime` shows offenders; heavy deps (torch, TF) imported lazily inside the function that needs them.
